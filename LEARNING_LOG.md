## M1 · Chunk 1.1: Repo + tooling

**Concepts**
- **Lockfile (`uv.lock`)**: pins the exact version of every dependency, including transitive ones, so eval numbers are reproducible later.
- **src/ layout**: tests import the *installed* package, which catches packaging mistakes a flat layout hides.
- **Typed config (pydantic-settings)**: one source of truth for knobs; bad values fail at startup, not deep inside a run. Precedence: kwargs > env > .env > YAML > defaults.
- **Secrets**: `.env` (gitignored) + `.env.example` (committed template); `SecretStr` keeps keys out of logs.
- **Git branches**: a branch is a movable pointer to a commit; `git switch -c <name>` creates one and moves you onto it. Work lands on `main` only via reviewed PRs.

## M1 · Chunk 1.2: Downloading papers from arXiv

**Concepts**
- **Corpus** = the collection of documents the system answers from (here: 400 arXiv papers, 2024+, on retrieval/RAG/evaluation).
- **Polite scraping**: arXiv asks for at most 1 request per 3 seconds, so the downloader sleeps between papers.
- **Restartable downloads**: papers already on disk are skipped, so a stopped run resumes.
- **Manifest** (`data/manifest.json`): the list of exact paper IDs + versions. Small enough to commit; lets anyone rebuild the same corpus without committing 150 MB of HTML.
- **Git**: commit = local save point; push = upload to GitHub (`git push -u origin <branch>`).

## M1 · Chunk 1.3: Cleaning the papers

**Concepts**
- arXiv HTML is generated by LaTeXML, which labels every part of a paper (`ltx_para`, `ltx_bibliography`...). We use those labels to keep prose and drop clutter.
- Dropped: menus, authors, figures, tables, footnotes, the reference list. Math is swapped for its plain LaTeX text.
- Output: one JSON per paper (`data/processed/`) with a title and a list of (heading, text) sections.
- Result: 273 KB of HTML became 31 KB of clean text for the sample paper; whole corpus is ~19.9M characters.
- Known tradeoff: tables are skipped for now, and a heading with no text of its own (e.g. "2 Related Work" directly followed by a subheading) is dropped.

**RAG in one sentence (asked about it mid-chunk)**
Search finds the relevant passages, then Claude answers using only those passages, with citations. If search returns the wrong passage, the answer will be wrong or empty, so retrieval quality is the thing we measure most.

## M1 · Chunk 1.4: Naive chunking

**Concepts**
- **Chunk** = a small passage (~200 words) that search can point to, instead of a whole 43,000-character paper.
- **Fixed-size with overlap**: slide along the text `size - overlap` words at a time. Overlap means a sentence cut at one boundary appears whole in the neighbouring chunk.
- **Deliberately naive**: it ignores sections, so it sometimes starts mid-sentence (chunk `2611.03179v1#004` begins "any clause receives a low score"). That is our baseline to beat with structure-aware chunking later, and we will measure the difference.
- **Chunk IDs** (`paper_id#index`) are how eval questions say "the answer is in chunk X" and how Claude's answers will cite sources.
- Size is counted in words for now (tokens would be more exact; revisit only if measurements say it matters).
- Result: 18,283 chunks, median 200 words.
